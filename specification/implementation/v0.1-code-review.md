## Findings

### 1. 🔴 HIGH — the deployed game is invisible to the engine

**`tools/run_on_pi.sh:73-77`**

```bash
USER_DIR="$PWD/userdata"
mkdir -p "$USER_DIR/games" "$USER_DIR/worlds"
ln -s "$PWD/game" "$USER_DIR/games/h11v"
```

The symlink is built and then nothing points the engine at it. Luanti has **no `--userdata` flag** —
verified against `--help` on 5.17: the only path options are `--world`, `--worldname`, `--worldlist`
and the deprecated `--map-dir`. The engine looks for games in its share path
(`/usr/share/games/luanti/games`, which holds `minetest_game`) and in its **user path**, which on the
device is `~/.minetest` (confirmed: 5.10 creates exactly that directory and not `~/.luanti`).

**Failure scenario:** `tools/deploy_to_term35.sh` copies the game, starts `run_on_pi.sh`, and the
engine exits with `Game "h11v" not found`. The deploy script's own liveness probe then reports "the
game did not stay up" and prints a log tail about a missing game — for a game that was copied
correctly, sitting on disk two directories away. Nothing in the pipeline would have caught this
before v0.6's round-trip, and the error points at the wrong thing.

**Fix:** link the deployed game into the engine's real user path, detecting `~/.luanti` vs
`~/.minetest` rather than assuming, and **verify the engine can actually see it** (`--gameid list`)
before launching, so this class of bug fails loudly at the point of cause instead of silently at the
point of effect.

### 2. 🟠 MEDIUM — the GPU confirmation reads a log nobody writes

**`tools/deploy_to_term35.sh:208`** greps for the renderer in:

```
~/$REMOTE_DIR/h11v.log   ~/.minetest/debug.txt   ~/.luanti/debug.txt
```

but **`run_on_pi.sh:81`** writes the engine log to `$PWD/h11v-debug.txt` — a fourth path, not in the
list. `~/h11v/h11v.log` holds only `run_on_pi.sh`'s own stdout, which contains no renderer line.

**Failure scenario:** every deploy finds no renderer string, so `$RENDERER` is empty and the whole
confirmation block is skipped. A device that had silently fallen back to `llvmpipe` would deploy,
run, and be measured — with the guard that exists precisely to prevent it reporting nothing at all.
A check that cannot fail is worse than no check, because it is trusted.

**Fix:** grep the path `run_on_pi.sh` actually writes, keeping the others as fallbacks.

### 3. 🟠 MEDIUM — sourcing the resolver can kill its caller silently

**`tools/luanti_path.sh:60-63`** ends with `return 1` when Luanti is not found. Callers source it as
`. tools/luanti_path.sh` and run under `set -e` (`deploy_to_term35.sh` uses `set -euo pipefail`).

**Failure scenario:** on a machine without Luanti, the caller dies at the `.` line with no output at
all — no "Luanti is not installed", no exit-code explanation. The contract the file documents ("a
caller can fail with its own message") is exactly what does not happen.

**Fix:** keep the return code for callers that check it, but also set an explicit
`LUANTI_MISSING=1` marker and document the `. tools/luanti_path.sh || true` idiom in the header, so
the caller reaches its own error path.

### 4. 🟡 LOW — a no-op in output a human reads

**`tools/gpu_preflight.sh:90`**: `echo "PASS: hardware renderer.${local_mode:+}"` — `${local_mode:+}`
always expands to nothing. Harmless, but it is in the success line someone reads at 2am, and a stray
expansion there invites the question "what was that supposed to say".

**Fix:** say which target passed.

### 5. 🟡 LOW — dead code in the asset gate

**`tools/check_assets.py:149-157`**, `Png.crop()` — written for a per-frame check of the animation
strips; the strips are verified by dimensions instead, so nothing calls it. Not wrong, just weight on
a file that is meant to be readable.

**Deferred to** cleanup / `/simplify`: it is dead rather than harmful, and removing it during a phase
whose gate is the same file is churn for no reduction in risk.

## What's solid

- **`tools/luanti_path.sh` earns its existence.** The two platforms genuinely differ (a separate
  `luantiserver` on Debian, `--server` on a bundled binary on macOS), and the function-not-variable
  choice is correct: it was made *because* zsh's lack of word-splitting had already produced a real
  failure, not defensively.
- **`gpu_preflight.sh` fails in the right direction.** An unreadable renderer string is treated as a
  failed preflight, not a pass — the one judgement call that matters in a check whose entire purpose
  is to refuse to be fooled.
- **`init.lua` documents the load order it does not yet have.** The commented `dofile` sequence with
  the reason for the order is more useful to v0.2 than an empty file would be.
- **`docs/decisions.md` records *why*, not just what.** The shaders-axis entry in particular turns a
  version number into a consequence, which is the whole point of the log.
- **The credential discipline held** under real use: the device password reached `sudo -S` over stdin
  during the install and never entered an argv, a log, or the repository.

## Fixes applied

All four fix-now findings landed in one focused commit, `d3d2214`, because they are one defect class
— the deploy path making assumptions about the engine that v0.1's probing disproved — and splitting
them would have produced three commits that only make sense read together.

### #1 — game linked into the engine's real user path, and verified

`run_on_pi.sh` now resolves the user directory (`~/.luanti` if present, else `~/.minetest`, creating
the latter), links the deployed game there, and **checks `--gameid list` for `h11v` before
launching**, exiting with a specific message if it is absent.

*Regression check:* the verification is inside the script. There is no unit-test harness for shell
tools and inventing one for four scripts would be the wrong trade — so the check that would have
caught this bug now runs on every single launch, on the device, which is strictly better than a test
that runs on the Mac. v0.6's deploy round-trip is its acceptance.

### #2 — the confirmation greps the log that is actually written

`deploy_to_term35.sh` now reads `~/$REMOTE_DIR/h11v-debug.txt` first, keeping the previous paths as
fallbacks for a device configured by hand.

*Regression check:* same mechanism — the grep now has a path that exists, so a `llvmpipe` fallback
produces the warning it was always supposed to.

### #3 — the resolver no longer kills its caller mutely

`luanti_path.sh` sets `LUANTI_MISSING=1` alongside the non-zero return, and its header documents the
`|| true` idiom. Callers that source it under `set -e` now reach their own error message.

### #4 — the no-op expansion is gone

The PASS line names the target it passed on.

### Architecture impact

**None to the seams.** The `NODES` table, the mutation rule table and `Perception → Intent` are
untouched — v0.1 registers nothing, so there is no contract to drift.

One documented behaviour did change, and it matters to v0.6: **the deployed game is made visible by
linking it into the engine's user path (`~/.minetest/games/`), not by any engine flag.** There is no
`--userdata` option. `tools/run_local.sh`, which v0.6 will write, must do the same thing on the Mac —
where the user path is the legacy `~/Library/Application Support/minetest/`, already recorded in
`docs/decisions.md`. This is now true of both platforms and should be treated as the way the game is
installed for a run, not a device-specific workaround.
