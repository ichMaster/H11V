# v0.1 — GitHub Issues

Issues for phase **v0.1 — Toolchain and skeleton** (version **v0 — The device: one player, one
island, at a measured frame rate**), derived from the per-phase Tasks in
[ROADMAP.md](../ROADMAP.md) (§v0.1) and the contracts in [ARCHITECTURE.md](../ARCHITECTURE.md)
(§Engine primitives, §The GPU path, §Repository layout). This file is scoped to a single phase; IDs
start the sequence (**H11V-001…004**).

The phase buys the two things every later phase depends on: an engine that actually runs on both
machines, and proof that the device renders on its GPU rather than on a software rasterizer. It ends
with the smallest possible game — a `game.conf` and an empty mod — selectable in Luanti's menu, so
that v0.2 has somewhere to put a block.

**Reconciled against the real tree (Step 0.5).** Three facts from the working tree shape these
issues and are not in the roadmap text:

- `tools/run_on_pi.sh` and `tools/deploy_to_term35.sh` already exist. `run_on_pi.sh` launches with
  `--gameid h11v`, which fixes the game's directory name (`games/h11v`) and its `name` in
  `game.conf`. H11V-003 must match that, or the deploy written in v0.6 will not find the game.
- `tools/check_lua.sh` already exists and currently passes vacuously ("no .lua files yet"). H11V-003
  is the commit that makes it a real gate, so its acceptance names that transition explicitly.
- `docs/` does not exist at all, though `ARCHITECTURE.md`, `SDLC.md` and `CLAUDE.md` all reference
  `docs/decisions.md` as the home for closed decisions. H11V-004 creates it rather than letting each
  later phase append to a file nobody defined.

## v0.1 — Toolchain and skeleton

### H11V-001 — Install Luanti on the Mac and pin the version

**Description:**
Install the engine on the development machine and record exactly which version this project is being
built against. Touches `tools/`, `docs/`. The version is not a detail: `ARCHITECTURE.md` §Acceptance
notes that basic shaders became mandatory in Luanti 5.11 and `enable_shaders` was removed, so the
graphics-profile ladder in v0.7 is only reproducible against a known version.

**What needs to be done:**
- `brew install --cask luanti` on the Mac.
- Confirm both the client and the headless server are reachable: the client binary, and
  `luantiserver` (or the equivalent the cask ships — record the real name if it differs, because
  `tools/test_worldgen.sh` in v0.2 will invoke it).
- Capture `luanti --version` verbatim.
- If the cask's binary is not on `PATH`, record the actual invocation path rather than papering over
  it with an alias — v0.2's headless gate has to call it non-interactively.

**Dependencies:** None

**Expected result:**
Luanti runs on the Mac, the headless server binary is identified by name, and the version string is
captured for the decisions log.

**Acceptance criteria:**
- [ ] The Luanti client launches on the Mac and its version string is captured.
- [ ] The headless server binary is located and its exact name recorded (it is the one `v0.2` will
      call; a wrong name there is a red gate nobody can explain).
- [ ] **Gate:** `tools/check_lua.sh` still green (vacuously — no `.lua` yet at this issue).
- [ ] Ties to the v0.1 DoD: the Mac Luanti version is available to be recorded in
      `docs/decisions.md` by H11V-004.

### H11V-002 — Install Luanti on the PocketTerm35 and pass the GPU preflight

**Description:**
Install the engine on the device over ssh and prove it will render on the Pi 5's V3D hardware rather
than on Mesa's `llvmpipe` software rasterizer. Touches `tools/`, `docs/`. This is the issue the whole
of v0 exists to de-risk: per [ARCHITECTURE.md](../ARCHITECTURE.md) §The GPU path, a software fallback
draws the world correctly and makes every frame-rate number in v0.7 fiction, so it must be caught
here and not discovered after a measurement session.

**What needs to be done:**
- Install Luanti on the device from the Pi OS repository (`apt install luanti`), falling back to an
  AppImage or Flatpak if the repository version lags materially behind the Mac's.
- Install `mesa-utils` and run the preflight: `glxinfo -B` / `eglinfo` must name **V3D** as the
  renderer, and `LIBGL_ALWAYS_SOFTWARE` must not be set in the device's environment.
- Capture the device's Luanti version and the renderer string verbatim.
- Note the installed version against the known aarch64 touch regression in 5.8
  ([VISION.md](../VISION.md) §risks; the roadmap names this as v0.1's first risk check). If the
  installed version is 5.8, say so loudly — it changes what v0.5 can assume about touch.
- Do **not** change the device's desktop configuration; `tools/run_on_pi.sh` already handles the Sway
  scale for the duration of a game and restores it afterwards.

**Dependencies:** None

**Expected result:**
The device has Luanti installed, and the renderer is demonstrably the V3D hardware driver.

**Acceptance criteria:**
- [ ] Luanti is installed on the PocketTerm35 and its version string is captured.
- [ ] **Gate (device):** the preflight names `V3D`; if any probe reports `llvmpipe`, `softpipe` or
      `swrast`, the issue fails rather than being recorded with a caveat.
- [ ] The device's Luanti version is checked against the 5.8 aarch64 touch regression and the finding
      is stated either way.
- [ ] Ties to the v0.1 DoD: the device version and renderer string are available to H11V-004.

### H11V-003 — Game skeleton: `game.conf` and an empty `h11_world`

**Description:**
The smallest thing Luanti will accept as a game: `games/h11v/game.conf` plus a mod directory with a
`mod.conf` and an `init.lua` that registers nothing. Touches `games/`. This is the structural gate
for the whole of v0 — every later issue puts content into the tree this one creates — and it is the
commit that turns `tools/check_lua.sh` from a vacuous pass into a real gate.

**What needs to be done:**
- `games/h11v/game.conf` with the game's name and description. The directory name **must** be `h11v`
  and the game id must match, because `tools/run_on_pi.sh` already launches with `--gameid h11v`.
- `games/h11v/mods/h11_world/mod.conf` declaring the mod name `h11_world`.
- `games/h11v/mods/h11_world/init.lua` — present, parses, registers nothing yet. Per
  [ARCHITECTURE.md](../ARCHITECTURE.md) §Components it will become `dofile` calls in a fixed order
  (nodes, mapgen, player); at this issue it is the empty shell with that order written down as a
  comment so v0.2 has an obvious place to land.
- Make the game visible to the Mac's Luanti (symlink or copy into the engine's `games/` directory —
  whichever the install in H11V-001 makes natural; record which, since `tools/run_local.sh` in v0.6
  will automate it).

**Dependencies:** H11V-001

**Expected result:**
"H11V" appears in Luanti's game list on the Mac and creating a world from it produces no errors.

**Acceptance criteria:**
- [ ] The game is selectable in Luanti's menu on the Mac and creates a world without errors in the
      engine log.
- [ ] The game id, the directory name and `run_on_pi.sh`'s `--gameid h11v` agree.
- [ ] **Gate:** `tools/check_lua.sh` green — and now non-vacuously: it reports at least one `.lua`
      file parsed.
- [ ] Ties to the v0.1 DoD: "the game is selectable in the menu and creates a world without errors".

### H11V-004 — Seed `docs/decisions.md` and record the v0.1 toolchain

**Description:**
Create the decisions log that `ARCHITECTURE.md`, `SDLC.md` and `CLAUDE.md` all already point at, and
write v0.1's findings into it. Touches `docs/`. The log is not a changelog: it is the place a closed
decision goes so a later phase does not silently reopen it, and it is where the
`Perception → Intent` contract's protection lives from v2 onward.

**What needs to be done:**
- Create `docs/decisions.md` with a stated format (date, decision, why) and `docs/device/` for the
  v0.7 measurement artefacts.
- Seed it with the decisions already taken and referenced across the specification, so the log starts
  honest rather than empty: the engine choice (Luanti, not Godot/Unity/Unreal), the bright-luminous
  art canon at 32×32 from a designed pack, and the three bots' names and needs triad.
- Record v0.1's own findings: the Mac Luanti version (H11V-001), the device Luanti version and the
  renderer string (H11V-002), and the headless server binary's real name.
- Note explicitly whether the graphics-profile ladder in v0.7 can use a shaders on/off axis, which
  follows directly from the installed version being below or at/above 5.11.

**Dependencies:** H11V-001, H11V-002, H11V-003

**Expected result:**
`docs/decisions.md` exists, carries the already-closed decisions, and records the v0.1 toolchain
facts that v0.7's measurements will be read against.

**Acceptance criteria:**
- [ ] `docs/decisions.md` exists with both Luanti versions and the device renderer string.
- [ ] The pre-existing closed decisions are recorded, each with its date and reason.
- [ ] The v0.7 shaders-axis consequence of the installed version is stated.
- [ ] **Gate:** `tools/check_lua.sh` green.
- [ ] Ties to the v0.1 DoD: "both Luanti versions and the device renderer string are recorded in
      `docs/decisions.md`".

## v0.1 scope notes

**Total effort:** ~1 week nominal (S+M+S+S); in practice bounded by the device install, which is the
only issue with real unknowns.
**Critical path:** H11V-001 → H11V-003 → H11V-004, with H11V-002 joining before the last.
**Phase DoD (roadmap §v0.1):** both Luanti versions and the device renderer string are recorded in
`docs/decisions.md`; the game is selectable in the menu and creates a world without errors.
**Contracts pinned this phase:** none of the architecture seams change. One structural commitment is
made and must stay consistent: the game id `h11v`, which `tools/run_on_pi.sh` already depends on.
**Device note:** a frame-rate budget is measured on the PocketTerm35 with the GPU preflight green,
never estimated on the Mac and never accepted from a software rasterizer; **no paid APIs** anywhere
in the acceptance path. No frame-rate claim is made in this phase — v0.1 only proves the preflight
can be passed.
