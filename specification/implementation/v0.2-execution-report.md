## Detailed results

### H11V-005 — the block catalogue as data
Eight rows and one loop. The row shape is the project's first seam, and required keys are asserted at
load: a later row omitting `groups` would otherwise ship a block nothing can dig. Turf carries a
three-element tile list with dirt explicitly in the middle, because Luanti's shorthand fill-in would
otherwise draw the green-fringed side texture on the block's underside.

### H11V-006 — the gate every later phase runs
Server → emerge → VoxelManip scan → one parseable line → shutdown, with the scanning mod under
`tools/` and never inside the game. All three v0.1 lessons are load-bearing here: the invocation
comes from `luanti_server()`, the port comes from the kernel rather than a guess, and the probe waits
for `emerge_area`'s callback instead of sampling a half-generated map.

Two judgement calls: the gate fails on any `ERROR[` in the engine log even when the probe reports ok
— a world that generates despite an error is built on something we do not understand — and every
assertion prints what it measured.

### H11V-007 — pointing the generator at our blocks
Only the three aliases v7 reads. The v6 trio's **absence** is the load-bearing part, so it is a
comment rather than nothing: register those under v7 and the world generates as bare stone with no
error, because they are accepted and never consulted. Surface layers come from one technical biome,
which v1.1's three real biomes will replace. Mapgen settings are registered as defaults, not
overrides, so an existing world keeps what it was created with — forcing them would silently change
terrain between runs, unacceptable when v0.7 measures a fixed seed.

### H11V-008 — the DoD, machine-checkable
Thresholds in the script, measurements in the probe. **Verified red:** pointing the biome's
`node_top` at stone produced `FAIL surface_top=h11_world:stone (need h11_world:turf)` and exit 1,
then reverted. Three consecutive runs are byte-identical.

## Code review

Four findings, all fixed in `012d7bb` — see [v0.2-code-review.md](v0.2-code-review.md). The one that
mattered: `water_source` was registered with `drawtype = "liquidsource"`, which **is not a Luanti
drawtype**. Unknown drawtypes are not errors; the engine falls back to a normal cube, so water would
have rendered as solid teal stone while behaving like water. `ARCHITECTURE.md` already specified
`"liquid"` — the document was right and was not followed.

## Architecture impact

No seam changed. The `NODES` row shape is now implemented as `ARCHITECTURE.md` describes it, and the
review moved the water drawtype *toward* the documented contract rather than away from it.

One observation for later phases: the engine-strictness list in `ARCHITECTURE.md` was correct and was
still not followed. v0.3 touches the same liquid plumbing, so its issues should quote that section
rather than paraphrase it.
